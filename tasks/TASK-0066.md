# TASK-0066: Implement Request Cancellation and Fallback Chain

## Objective
Build client disconnect detection that aborts upstream provider requests within 500ms, and the fallback chain that tries alternative providers when the primary fails.

## Context
When a client disconnects, the gateway must stop the upstream request to avoid wasting provider tokens. Fallback chain tries backup providers. See ARCHITECTURE.md section 4.1 and EPICS.md Epic-13.

## Acceptance Criteria
- [ ] `crates/gateway-core/src/cancellation.rs` — cancellation token propagation
  - Detects client disconnect via Axum's `Body` stream end
  - Propagates cancellation to upstream request via `tokio::select!`
  - Aborts upstream within 500ms of client disconnect
- [ ] `crates/gateway-core/src/fallback.rs` — fallback chain execution
  - Executes fallback chain sequentially: primary → backup 1 → backup 2
  - Each fallback attempt logged with provider, error, latency
  - Fallback exhausted → return 502 with `all_providers_failed` error
  - Each attempt gets its own retry logic
- [ ] Cancellation + fallback interaction:
  - Client disconnect during fallback → cancel current attempt
  - Don't try remaining fallback providers after disconnect
- [ ] Request context includes `CancellationToken` throughout lifecycle

## Technical Notes
- Use `tokio_util::sync::CancellationToken` for propagation
- In handler: `let token = CancellationToken::new(); token.cancelled() → detect disconnect`
- Use `tokio::select!` in the HTTP request: `biased; token.cancelled() => break, response = provider.call() => handle`
- Fallback chain: `Vec<Box<dyn Provider>>` from routing engine
- Each fallback: clone request, retry, check circuit breaker
- Log: `fallback_attempt{provider, attempt, error, latency_ms}`
