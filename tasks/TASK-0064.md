# TASK-0064: Implement Retry Logic with Exponential Backoff

## Objective
Build the retry mechanism for provider requests with exponential backoff and configurable retry policies.

## Context
On provider errors (5xx, 429, timeout), the gateway retries before attempting fallback providers. See ARCHITECTURE.md section 4.1 step 8 and EPICS.md Epic-13.

## Acceptance Criteria
- [ ] `crates/gateway-core/src/retry.rs` — retry implementation
  - `RetryPolicy` struct: max_retries (default 2), backoff_base_ms (default 1000), retry_on_status: Vec<u16>
  - Exponential backoff: 1s, 2s delays between retries
  - Jitter: random component added to backoff (±25%) to prevent thundering herd
  - Only retries on: 5xx, 429, timeout — NOT on 4xx client errors
- [ ] `RetryExecutor` that wraps provider calls
  - Tracks retry count per request
  - Returns `RetryResult: Success(response) | Exhausted(last_error)`
- [ ] Per-provider retry policy configurable in provider config
- [ ] Each retry attempt logged with provider, error, latency
- [ ] Request cancellation propagates to abort retries

## Files Affected
- `crates/gateway-core/src/retry.rs` — retry implementation
- `crates/gateway-core/src/lib.rs` — module export
- `crates/gateway-db/src/models.rs` — RetryPolicy config struct

## Dependencies
- TASK-0033 (request orchestrator)
- TASK-0021/0022 (provider adapters)

## Technical Notes
- Use `tokio::time::sleep` for backoff delays
- Use `tokio::select!` with ` tokio::time::timeout` for cancellation
- Jitter: `backoff + (backoff * 0.25 * random::<f64>())`
- Do NOT retry on: 400, 401, 403, 404 (client errors)
- Max total retry time: sum(backoffs) < 10 seconds
- If all retries exhausted: return `ProviderError` for fallback handling

## Test Requirements
- Unit test: retry on 503, success on 2nd attempt
- Unit test: no retry on 400 (client error)
- Unit test: exponential backoff increases delay
- Unit test: cancellation aborts retries
- Unit test: max retries not exceeded
