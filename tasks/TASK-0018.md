# TASK-0018: Implement Key Revocation and Cache Invalidation

## Objective
Build immediate API key revocation with Redis cache invalidation and pub/sub event propagation.

## Context
Key revocation must propagate within 100ms. This requires deleting the cached key entry from Redis and publishing an invalidation event. See AUTH.md section 2.5 and EPICS.md Epic-03.

## Acceptance Criteria
- [ ] `DELETE /api/v1/organizations/{org_id}/keys/{key_id}` revokes key (sets status='revoked')
- [ ] Revocation immediately deletes Redis cache entry `auth:apikey:{key_hash}`
- [ ] Publishes `apikey:revoked` event to Redis pub/sub with `{ key_hash, key_id, timestamp }`
- [ ] Any request in flight with the revoked key fails within 100ms
- [ ] Audit log entry created: action=`api_key.revoked`, with actor_id and timestamp
- [ ] Revoked keys appear in list with status filterable
- [ ] Cannot revoke an already-revoked key (returns 409)

## Files Affected
- `crates/gateway-auth/src/api_key.rs` — revoke logic
- `crates/gateway-auth/src/cache_invalidator.rs` — pub/sub invalidation
- `crates/gateway-db/src/repos/api_key_repo.rs` — revoke method
- `crates/gateway-db/src/repos/audit_repo.rs` — audit logging
- `crates/gateway-api/src/routes/keys.rs` — HTTP route

## Dependencies
- TASK-0015 (API key validation middleware with cache)
- TASK-0016 (RBAC — only admins can revoke keys)

## Technical Notes
- Use `redis::aio::MultiplexedConnection` for pub/sub
- Invalidation subscriber runs as a background task (tokio::spawn)
- On `apikey:revoked` event: delete from local in-memory cache if any
- Include `revoked_at` and `revoked_reason` fields on update
- Transaction: UPDATE status + INSERT audit_log entry

## Test Requirements
- Integration test: revoke key, subsequent request with same key returns 401 within 100ms
- Integration test: revoke already-revoked key returns 409
- Unit test: audit log entry created on revocation
- Unit test: pub/sub event contains correct key_hash
