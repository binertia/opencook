# TASK-0033: Integrate Routing Engine into Request Orchestrator

## Objective
Integrate the rule evaluation engine into the request lifecycle so that every chat completion request is routed through the routing engine before being sent to a provider.

## Context
The orchestrator coordinates the 12-step request lifecycle. Routing happens after cache check (step 6) and before request transformation (step 7). See ARCHITECTURE.md section 4.1.

## Acceptance Criteria
- [ ] `crates/gateway-core/src/orchestrator.rs` — request orchestrator updated
  - Step 6: Load active routing rules for org + model
  - Step 7: Evaluate rules → select provider
  - Step 8: Transform request to provider-native format
  - Step 9: Call provider (with retry logic)
  - Step 10: Transform response to OpenAI format
- [ ] Orchestrator uses adapter factory to create provider instance from config
- [ ] Routing rule ID stored in `requests.routing_rule_id` column
- [ ] If no rules match → default behavior (direct model-to-provider lookup)
- [ ] Retry logic: on 5xx/429/timeout, retry up to 2 times with exponential backoff (1s, 2s)
- [ ] If retries exhaust and fallback chain exists → try next provider

## Files Affected
- `crates/gateway-core/src/orchestrator.rs` — updated orchestrator
- `crates/gateway-core/src/retry.rs` — retry logic with backoff

## Dependencies
- TASK-0032 (rule evaluation engine)
- TASK-0027 (chat completions handler)
- TASK-0021/0022 (provider adapters)

## Technical Notes
- Use `tokio::time::sleep` for backoff delays
- Use `tokio::select!` with timeout for provider calls
- Retry only on transient errors: 5xx, 429, timeout
- Do not retry on 4xx client errors
- Fallback chain consumed sequentially
- Each fallback attempt logged with provider name, error, and latency

## Test Requirements
- Integration test: request routed to correct provider based on rule
- Integration test: fallback chain works when primary fails
- Integration test: retry with exponential backoff on 503
- Integration test: no retry on 400 (client error)
- Integration test: routing_rule_id in DB matches expected rule
