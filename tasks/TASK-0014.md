# TASK-0014: Implement API Key Generation and Storage

## Objective
Build the API key generation system that creates `sk-gw-{base58}` keys, stores only SHA-256 hashes, and displays the full key exactly once on creation.

## Context
System A authentication for LLM API consumers. API keys use a URL-safe base58 format. Only the hash is persisted — the full key is shown once. See AUTH.md section 2 and EPICS.md Epic-03.

## Acceptance Criteria
- [ ] `crates/gateway-auth/src/api_key.rs` — key generation with base58 encoding and CRC-32C checksum
- [ ] Key format: `sk_gw_{base58_random_32}{base58_checksum_6}` = 47 chars total
- [ ] SHA-256 hash of full key stored in `api_keys.key_hash` column
- [ ] 8-character prefix stored in `api_keys.key_prefix` for UI display
- [ ] Key generation rate-limited: max 10 keys/minute per organization
- [ ] `POST /api/v1/organizations/{org_id}/keys` returns full key only on creation in `key_full` field

## Files Affected
- `crates/gateway-auth/src/api_key.rs` — key generation and hash storage
- `crates/gateway-auth/src/models.rs` — ApiKeyCreateRequest, ApiKeyCreateResponse structs
- `crates/gateway-db/src/repos/api_key_repo.rs` — key CRUD operations

## Dependencies
- TASK-0008 (api_keys table migration)
- TASK-0012 (user/org context for key creation)

## Technical Notes
- Use `base58` crate (or implement with `bs58`) for encoding
- Use `crc32c` crate for checksum computation
- Use `rand::thread_rng()` for CSPRNG random bytes (24 bytes = 32 base58 chars)
- Full key only shown in create response; list/GET endpoints never include it
- Include key name, scopes array, allowed_models, expires_at in creation

## Test Requirements
- Unit test: generated keys match regex `^sk_gw_[A-Za-z0-9]{38}$`
- Unit test: same random bytes produce same key (deterministic)
- Unit test: different random bytes produce different keys
- Unit test: hash verification — store hash, verify full key matches
- Integration test: create key returns full key, subsequent GET does not
