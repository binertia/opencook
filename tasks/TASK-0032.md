# TASK-0032: Implement Rule Evaluation Engine

## Objective
Build the rule evaluation engine that selects the best provider for each request based on routing rules, provider health, and configured strategy.

## Context
The evaluation engine is the core of the routing system. It checks rules in priority order, evaluates conditions, and applies the strategy to select a provider. See ARCHITECTURE.md section 4.1 step 6 and EPICS.md Epic-06.

## Acceptance Criteria
- [ ] `crates/gateway-core/src/router.rs` — rule evaluation engine
  - `evaluate_rules(request, rules, health_status) -> ProviderSelection`
  - First matching rule wins (priority order)
  - Condition evaluation against request properties
- [ ] `Strategy` enum: Single, Fallback(Vec<Target>), Weighted(Vec<Target>), Conditional
  - `Single` → one provider
  - `Fallback` → try primary, then backup chain on failure
  - `Weighted` → distribute by weight (random selection)
- [ ] Health check: unhealthy providers skipped unless `require_health_check: false`
- [ ] `ProviderSelection` struct: provider_name, provider_config, fallback_chain
- [ ] No healthy provider available → `503 Service Unavailable` with `X-Unavailable-Reason: no_healthy_provider`
- [ ] Routing decision logged to `requests.routing_rule_id` for traceability

## Files Affected
- `crates/gateway-core/src/router.rs` — evaluation engine
- `crates/gateway-core/src/lib.rs` — module export
- `crates/gateway-core/src/strategies.rs` — strategy implementations

## Dependencies

## Technical Notes
- Condition evaluation: JSON conditions compared against request properties
- Conditions support: model regex match, required capabilities, max latency
- Weighted strategy: generate random number 0..sum(weights), select target
- Fallback chain constructed as `Vec<Box<dyn Provider>>` from factory
- Cache compiled conditions (regex) to avoid recompilation per request
- Target benchmark: rule evaluation < 1ms per rule

## Test Requirements
- Unit test: single rule matches model name → correct provider selected
- Unit test: fallback strategy tries primary then backup on failure
- Unit test: weighted strategy distributes by weight (statistical test)
- Unit test: unhealthy provider skipped when health check required
- Unit test: no matching rules → 503 with correct header
- Performance test: evaluate 10 rules in < 1ms
