# TASK-0041: Implement Sliding Window Rate Limiter with Redis Lua

## Objective
Build the Redis-backed sliding window rate limiter using atomic Lua scripts for per-key limits (requests/minute, tokens/minute).

## Context
Rate limiting must be race-condition-free and fast. Redis Lua scripts execute atomically, preventing burst-through. See CACHE.md section 4 and EPICS.md Epic-08.

## Acceptance Criteria
- [ ] `crates/gateway-quota/src/rate_limiter.rs` — sliding window rate limiter
  - `check_limit(key: &str, limit: u64, window_secs: u64) -> LimitResult`
  - Uses Redis Lua script for atomic check-and-record
  - Returns: `Allowed { remaining, reset_at }` or `Exceeded { retry_after }`
- [ ] Lua script atomically:
  1. Removes entries outside the sliding window (ZREMRANGEBYSCORE)
  2. Counts entries within window (ZCARD)
  3. If under limit: adds current request (ZADD) + sets expiry
  4. Returns 1 (allowed) or 0 (denied)
- [ ] Rate limit headers on every response: `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`
- [ ] p99 check latency < 5ms
- [ ] Different window types: requests per minute, tokens per minute
- [ ] Key format: `ratelimit:{key_id}:{window_type}`

## Technical Notes
- Use `redis::Script` for Lua script execution
- Script operates on single key (hashed to one Redis slot for cluster compat)
- Sorted set score = request timestamp in milliseconds
- Token rate limiting: use `tokens` as weight in sorted set (score = timestamp, member = count)
- Use `redis::pipe()` for pipelining multiple rate limit checks
- Handle Redis script failure: fail open (allow request) with warning log

## Test Requirements
- Unit test: requests under limit are allowed
- Unit test: request at limit is denied
- Unit test: window slides — old requests expire
- Unit test: concurrent requests don't exceed limit (race condition test)
- Performance test: rate limit check < 5ms p99
