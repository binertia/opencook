# TASK-0072: Implement Webhook CRUD and Delivery System

## Objective
Build the webhook CRUD API, delivery system with retry (3 attempts, exponential backoff), and signature verification.

## Context
Webhook infrastructure for event notifications. Webhooks are POST requests with HMAC-SHA256 signatures, retried up to 3 times on failure. See DATABASE.md sections 2.12-2.13 and EPICS.md Epic-15.

## Acceptance Criteria
- [ ] `crates/gateway-db/src/repos/webhook_repo.rs` — webhook CRUD
  - `create`, `get_by_id`, `list_by_org`, `update`, `delete`
  - All queries include `WHERE org_id = $1`
- [ ] `crates/gateway-db/src/repos/webhook_delivery_repo.rs` — delivery tracking
  - `create_delivery`, `update_delivery_status`, `list_deliveries`
  - Delivery status: queued, in_progress, completed, failed
- [ ] Webhook payload structure:
  - `{ event, timestamp, delivery_id, data }`
  - HMAC-SHA256 signature in `X-Webhook-Signature` header
  - Signature: `hex(HMAC-SHA256(secret_key, payload_json))`
- [ ] Admin API: `GET/POST/PUT/DELETE /api/v1/organizations/{org_id}/webhooks`
- [ ] Secret key stored encrypted (AES-256-GCM, same as provider keys)
- [ ] Webhook signing secret displayed once on creation

## Technical Notes
- Use `hmac` crate with `sha2::Sha256` for signature generation
- Secret key: 32-byte random string (base64-encoded for display)
- Delivery attempts: 3 retries with exponential backoff (5s, 25s, 125s)
- Delivery logging: each attempt recorded with status code, response body preview
- Timeout per attempt: 30 seconds
- Webhook delivery uses `reqwest::Client` with timeout
