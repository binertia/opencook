# TASK-0029: Implement Request Logging and Response Metadata

## Objective
Build the request logging pipeline that records every LLM API request to PostgreSQL with full metadata asynchronously.

## Context
Request logging is critical for analytics, cost tracking, and debugging. Logs must not block the response path. See DATABASE.md section 2.7 (requests table) and ARCHITECTURE.md section 4.1 step 11.

## Acceptance Criteria
- [ ] `crates/gateway-observability/src/request_logger.rs` — async request logger
  - Bounded channel (capacity 1000) for fire-and-forget logging
  - Background worker consumes channel and writes to DB
  - On backpressure: drop oldest entries (log warning)
- [ ] Every request logged to `requests` table:
  - trace_id, org_id, api_key_id, provider_config_id, model_requested, model_routed
  - prompt_tokens, completion_tokens, total_tokens
  - input_cost, output_cost, total_cost (computed from model pricing)
  - latency_gateway_ms, latency_provider_ms, latency_total_ms
  - status, status_code, error_code, error_message
  - cache_hit boolean
- [ ] `crates/gateway-observability/src/cost_calculator.rs` — cost calculation
  - `calculate_cost(model_id, prompt_tokens, completion_tokens) -> CostBreakdown`
  - Uses pricing from model registry
- [ ] Corresponding `responses` table entry created with response body (truncated at 64KB)

## Technical Notes
- Use `tokio::sync::mpsc::channel(1000)` bounded channel
- Logger worker: `while let Some(record) = rx.recv().await { write_to_db(record) }`
- Cost calculation: `input_cost = prompt_tokens * input_cost_per_1k / 1000`
- Request body truncated to 64KB; set `request_body_truncated = true` if truncated
- Use `tokio::spawn` for logger worker, survives the request handler
- Handle DB write failures: retry once, then log to stderr and drop

## Test Requirements
- Unit test: cost calculation produces correct values for known pricing
- Integration test: request logged after completion with correct token counts
- Integration test: failed request logged with error_code
- Integration test: body truncation works for large requests (> 64KB)
- Performance test: logging adds < 1ms overhead (channel send is non-blocking)
