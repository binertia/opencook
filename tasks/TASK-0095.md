# TASK-0095: Implement Multi-Organization Support and Org Switching

## Objective
Build the backend and frontend support for users belonging to multiple organizations with organization switching.

## Context
Users may be members of multiple organizations (e.g., work and personal). The gateway must support org switching and isolated data per organization. See EPICS.md Epic-20.

## Acceptance Criteria
- [x] `user_organizations` junction table (new migration):
  - `user_id`, `org_id`, `role`, `joined_at`, `created_by`
  - Unique constraint on `(user_id, org_id)`
  - Soft-delete not needed (remove row on leave)
- [x] Backend: user can belong to multiple organizations
  - `GET /api/v1/auth/me` returns list of organizations with roles
  - `POST /api/v1/auth/switch-org` switches active organization
  - Active org stored in JWT claim: `active_org_id`
  - All API calls scoped to active org
- [x] Frontend: org switcher in header
  - Dropdown showing all user's organizations
  - Click to switch (refreshes page with new org context)
  - Current org highlighted
- [x] Org creation:
  - `POST /api/v1/organizations` — create new organization
  - Creator becomes owner automatically
  - Can invite users immediately
- [x] Org isolation enforced:
  - All data queries include active org_id
  - Cross-org access returns 403
  - Cache keys include org_id prefix

## Technical Notes
- Junction table: no soft-delete (hard delete on leave org)
- JWT claim: `active_org_id` set on switch, re-issued token. Backward compat: old tokens with `org_id` are promoted to `active_org_id` during verify.
- Frontend: store active org in localStorage; on switch invalidate all TanStack Query caches and reload page
- Org creation: rate-limited to 5 orgs/hour per user via Redis; slug auto-generated with collision handling; creator auto-assigned as owner
- API key auth: previously stubbed with `DEFAULT_ORG_ID`; now performs real DB lookup by SHA-256 hash with constant-time verification

## Security & Edge Cases Handled
1. **Switch-org validation**: `POST /v1/auth/switch-org` queries `user_organizations` to verify membership before issuing new JWT. Returns 403 if user is not a member.
2. **Cross-org access**: Existing tenant isolation middleware (`tenant_isolation_middleware`) already checks URL path org_id against auth org_id. All handlers use `auth.org_id` for data queries.
3. **API key scoping**: API keys are now looked up by hash in the database; the returned `org_id` from the key record is used in `AuthContext`, preventing cross-org access via leaked keys.
4. **Rate limit org creation**: Redis-based rate limiter prevents abuse (5 orgs/hour/user).
5. **Slug uniqueness**: Enforced at DB level with `UNIQUE INDEX`; application layer handles collisions by appending random suffix.
6. **Input sanitization**: Org names and billing emails are sanitized before DB insertion.
7. **Audit logging**: All org creations and switches are logged to the audit log.
8. **Old token handling**: When a user switches org, the old token remains valid for its remaining lifetime (up to 15 min) but is scoped to the old org. This is acceptable and documented.
9. **SQLite SOLO support**: The `user_organizations` table is included in the SOLO mode schema initialization.
