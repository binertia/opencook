# TASK-0037: Implement L1 In-Process Cache with moka

## Objective
Build the L1 in-process cache using the `moka` crate with LRU + TTL eviction, 10K entry capacity.

## Context
L1 cache provides sub-millisecond lookups for hot entries. Uses the `moka` crate which offers async-aware caching with TTL and LRU eviction. See CACHE.md section 1.2 and EPICS.md Epic-07.

## Acceptance Criteria
- [ ] `crates/gateway-cache/src/l1_cache.rs` — L1 cache implementation
  - Uses `moka::future::Cache<String, CachedResponse>`
  - Max capacity: 10,000 entries (configurable)
  - TTL: 60 seconds (configurable)
  - LRU eviction when capacity exceeded
- [ ] `L1Cache` struct with methods:
  - `get(key: &str) -> Option<CachedResponse>`
  - `insert(key: String, value: CachedResponse)`
  - `invalidate(key: &str)`
  - `invalidate_all()`
  - `stats() -> CacheStats` (hit count, miss count, size)
- [ ] Cache stats exposed via Prometheus metrics
- [ ] L1 cache created once at startup and shared via `Arc`
- [ ] Thread-safe: moka handles concurrent access internally

## Files Affected

## Technical Notes
- Use `moka::future::Cache::builder().max_capacity(10000).time_to_live(Duration::from_secs(60)).build()`
- Key format for L1: same as cache key hash (no org_id prefix needed since L1 is per-process)
- CachedResponse stored in L1 as cloned value
- On L2 hit: promote entry to L1 automatically
- On invalidation: remove from both L1 and L2
- Use `crossbeam` for internal synchronization (moka dependency)

## Test Requirements
- Unit test: insert + get returns cached value
- Unit test: TTL expiry — entry not returned after TTL
- Unit test: LRU eviction — oldest entries evicted at capacity
- Unit test: concurrent insert/get does not panic
- Performance test: L1 get latency < 0.1ms (100μs)
