# TASK-0040: Implement Cache Metrics and Analytics

## Objective
Build cache metrics collection (hit rate by layer, by model) and analytics storage in the cache_metadata table.

## Context
Cache metrics enable monitoring and optimization. The `cache_metadata` table tracks cache entry metadata for analytics. See CACHE.md section 7 and DATABASE.md section 2.14.

## Acceptance Criteria
- [ ] `crates/gateway-cache/src/metrics.rs` — cache metrics
  - `cache_hit_l1_total` counter — L1 hits
  - `cache_hit_l2_total` counter — L2 hits
  - `cache_miss_total` counter — misses
  - `cache_hit_by_model_total` counter — per-model breakdown
  - `cache_cost_saved_total` counter — estimated cost savings
- [ ] Metrics emitted via Prometheus-compatible format at `/metrics`
- [ ] Cache metadata stored in `cache_metadata` table on cache insert:
  - cache_key_hash, model_id, prompt_preview (first 200 chars), prompt_tokens
  - ttl_seconds, expires_at, hit_count (incremented on each hit)
- [ ] `crates/gateway-cache/src/analytics.rs` — cache analytics queries
  - `get_hit_rate(org_id, period) -> f64`
  - `get_cost_saved(org_id, period) -> f64`
  - `get_top_cached_models(org_id, limit) -> Vec<ModelCacheStats>`
- [ ] Admin API: `GET /api/v1/cache/stats` — cache statistics

## Technical Notes
- Use `metrics` crate for counters: `metrics::counter!("cache_hit_total", "layer" => "l1")`
- Cost saved: (provider cost of cached request) × (hit_count - 1)
- Cache metadata upsert: insert on first cache, update hit_count on hits
- Use background task to batch metadata updates (not per-request)
- Analytics queries use `usage_records` table for cost data (not requests)
